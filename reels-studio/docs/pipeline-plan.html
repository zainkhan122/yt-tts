3. Step by step: what happens, who decides, and what I produce

For each step: the decision, the guideline I read first, and the output that goes into the brief.

Step 1 · Sense · code

1Daily intake, 24-hour window

Collect new items from GitHub trending, Hugging Face, GitTrend, the TikTok and YouTube channels in the registry, and the news and product pages in research/sources.csv. Each item keeps its URL, the time it appeared, and its raw text.

Default: an item is eligible if it appeared in the last 24 hours. Older items need a note in the brief explaining why they are still worth making.

Output: intake/YYYY-MM-DD.json (raw items, no judgment yet)

Step 2 · Read & classify · agent

2I read each item and decide what it is

I open the source, read it, and write one line: what the thing is, who made it, and what someone could do with it. The category is my label for that content, such as a tool, a repo, a model, a free offer, or news. There is no host lookup and no fixed list.

Example: a GitHub repo that is a free-model proxy is a free offer / tool, not a "repo". A Hugging Face model card with a sales page is a product.

Output: a one-line judgment per item, with the source link.

Step 3 · Judge & choose · agent + analytics

3I decide what to make, and why

I score each item on the signals in section 5, then write the reason for each pick. I also look at our analytics: which topics, hooks and formats performed well recently. That is a guide, not a quota.

Output: 1 to 3 picks per day, each with a paragraph explaining the choice and the data behind it.

Owner decision: how many items per day (section 8).

Step 4 · Verify claims · code + agent

4Every claim must trace to a source

Each number, capability or comparison the video will state is listed and matched to a line in the maker's own page, README or docs, or to a run I did. A claim with no match is rewritten or dropped. The checks are in section 4.

Stops here: a claim with no source line. Example: "no usage cap" with no maker text saying so. That is an owner decision, not a silent pass.
Step 5 · Plan the video · agent

5Decide how this tool should be shown

I write a per-tool plan: the viewer's question, the hook, the story beats, the proof moment, what the viewer should try, and the visuals this tool needs. I do not use a template. I start from the tool's own media and create what is missing.

Example plan: for a tool with a terminal install, the proof is the install output shown live in a terminal graphic; for a tool with only a web UI, the proof is a before and after of the UI.
Step 6 · Make the media · agent

6Use the maker's media, then make what is missing

Use the maker's own screenshots, logos and clips. Where media is thin, I make a per-tool asset: an animation, a chart, a diagram, or a transition built for that tool's story. No shared layouts. Nothing is filmed.

Example: for a tool that runs a model on a laptop, the graphic is a memory bar that fills as the model loads. For a tool that removes ads, it is the home-screen rows disappearing one at a time.
Step 7 · Script & copy · agent

7Open on the viewer's question

The script opens on the question the viewer has, then shows what the tool does for them, in plain speech. No sources, legal text or citations in the spoken script, the captions, or the copy. Sources stay only in the internal brief fields.

Example opening: "Is your Android TV home screen full of ads?" then the cleanup, in plain words.
Step 8 · Voice & align · code

8Words match the audio

The voice is generated, then checked against the script. The match threshold lives in one file, config/gates.json. If a line fails, the code reports the exact expected and heard words, and I fix the script.

Step 9 · Render & QA · code + agent

9Render, then check the picture

The code checks format, length, loudness, peak level and that frames are not blank. I review the frames for layout, readability and whether the proof shows. A failure goes back to step 6 or 7 with the specific reason.

Step 10 · Publish & learn · code + agent

10Publish, read back, learn

Schedule through Buffer after a read-back check. After publishing, metrics go to the analytics files. That data feeds step 3 for the next choice.

7. Guidelines I work from, with examples (replacing templates)

Guidelines describe the judgment, with examples of good and bad. They do not fill in a fixed layout. Each one is a file I read before the step.

Hook guideline

Open on what the viewer wants to know, in their words, within the first 3 seconds. Only then name the tool.

"Is your Android TV home screen full of ads?"
"Introducing a new open-source cleanup tool." (product announcement, no viewer question)

Explain guideline

Say what the tool does for the viewer in one plain sentence, then show it working. No adjectives that the video does not prove.

"It removes the ad rows, and it runs over Wi-Fi with no root."
"The best-in-class, revolutionary way to clean your TV."

Media guideline

Use the maker's media first. If it does not show the proof, make an asset that does. Each asset must answer one question the viewer has.

Terminal graphic for an install command; a memory bar for a model that needs RAM; a before and after for a UI tool.
The same card layout reused for every tool.

Claim guideline

A number or capability is said only if a source line supports it. If it cannot be supported, rephrase it to what is shown, or drop it.

"Runs a 35-billion-parameter model on a laptop" if the maker's docs say so.
"No usage cap" with no matching maker text. Held for owner decision.

Description guideline

Describe what the viewer will see and do. One link: the tool's own page. No legal, privacy, licence or terms links.

"Clean your Android TV home screen without root. Link: the project page."

Pick guideline

Write the viewer gain, the demand signal, the traction, the competition, and the risk, then decide. Check our analytics before choosing the format.

A pick with an unsupported claim is not dropped; it is held, and the owner decides.
