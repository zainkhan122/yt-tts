# Capability-aware visual execution prototype

Experimental only. No publishing integration and no external generation providers are configured by this change. Do not use these modules as a production or security boundary.

## Audit and integration points

- `graphics/production/semantic.py` validates the AI's descriptive plan; `scheduler.py` produces timed beats/events after in-process audio-alignment validation. Its serialized output is not a cryptographic proof of alignment. `execution.py` consumes that scheduled shape, but cannot prove the origin or correctness of a loaded blueprint.
- `graphics/production/providers.py` previously had only a simple capability-name registry. It now also has opt-in `VisualCapabilities`/`VisualRegistry`; the legacy classes are unchanged. Each visual profile explicitly declares operation, format, dimensions, duration, image-to-video, reference, subject-consistency, transparency, camera and object-motion support, and configuration/auth/availability state. These are operator/adapter declarations, **not dynamically verified provider claims**. `status()` distinguishes unsupported, unconfigured, unauthorized, authorization-unknown, unavailable, unknown and available.
- `graphics/render.py` and `graphics/templates/` provide deterministic Playwright/FFmpeg graphics and selected motion templates. `graphics/production/render.py` draws three specialized schematic scenes; it cannot render general semantic events, image-to-video assets, or arbitrary clips. No generic bridge is assumed.
- `graphics/media.py` and `lib/cover_frame.py` use FFmpeg; `tools/capture_store.py` stores captured proof assets in GitHub Releases and `tools/cover_store.py` manages covers. They have different lifecycles; the new local request-keyed cache does not replace or upload to them.
- No repository image, video or image-to-video generation API was verified as configured/authorized. Prior interactive image tool is not a repository API. Blender is not on PATH. OpenRouter agent pilot is `paused_by_owner`; it remains paused and is text planning, not verified visual generation. This audit did not attempt to discover or print secrets.

## Module contracts

`build_execution(scheduled_blueprint, registry, policy, width=..., height=..., allow_deviation=False)` chooses only available registered operations. `policy` maps a treatment to ordered explicit `{provider, operation, deviation?}` choices. It checks dimensions, duration, declared treatment, camera, references and actual-object-motion capability. An unsupported treatment may use an explicitly marked fallback only when `allow_deviation=True`. Object-motion requests cannot silently fall back to stills. This is a declarative *plan*, not evidence that a provider actually animates the requested subjects. Selection is not semantic verification; author/provider capability declarations and output need review. It supports selectable image, video, image-to-video, programmatic and composite operation names, but no actual adapter for those operations is included.

`AssetStore` accepts a registered adapter with `generate(request, output_path)`; the adapter must return only after writing the file. It validates PNG/JPEG using Pillow or MP4 metadata and full FFmpeg video decode, hashes content, records provider/model/prompt, dimensions/duration and beat/event associations, and stores media outside JSON. Request hash includes prompt, provider/model, parameters, continuity and reference content hashes. A local file lock serializes identical requests; validated files are reused. `force=True` regenerates one request; `reuse()` associates a verified prior asset to another event. Reference images are validated and passed by local path only when explicitly supported. `RetryableAssetError` means the adapter has verified a safe-to-retry failure; other exceptions, especially uncertain remote requests, are not retried automatically. Temporary files are cleaned at exit. This is a local synchronous prototype, not a distributed queue.

`Continuity` records desired subject, setting, lighting, palette, camera and reference IDs. It does not prove identity consistency; reference support and actual output must be evaluated. `to_render_instructions` validates asset hash, media and a renderer's explicitly supplied capability contract; it returns data only. The actual current legacy renderer is explicitly marked incompatible (`LEGACY_RENDERER`) with arbitrary generated media; supplying an invented contract does not create a renderer.

## Test results and limitations

Tests in `tests/test_visual_execution.py` use fake in-process adapters and a generated single-color FFmpeg video to verify orchestration, not meaningful object animation or a real AI provider. No real semantic planner or alignment provider was used. The smartphone acceptance demonstration **has not been achieved**, and no photorealistic smartphone or animation was generated through this engine. No claim of independent battery interpretation or audiovisual quality is made.

Missing before production: actual provider adapters and authorization/capability discovery, an executor for semantic object actions and programmatic templates, compositor and real renderer bridge, multi-asset composition and chained image-to-video orchestration, proven subject consistency, async durable jobs, bounded adapter/network execution, remote idempotency, recovery state and safe cache retention, asset rights/provenance, secure path and untrusted media isolation, output-specific moderation, strict revalidation of alignment receipt across processes, robust video stream/container probing and decode limits, verified output dimensions, and full human audiovisual/quality review. A format/capability declaration or a valid MP4 does not prove any requested object moved. No publishing changes were made.
