# Review-only layer-rendering proof: smartphone battery

## Architecture audit

`semantic.py` defines structured beats and visual events. `scheduler.py` binds event phrases to timestamps from an in-process trusted alignment report; `execution.py` chooses declared provider operations, but does not render them. `providers.py` advertises explicit configured capabilities; `assets.py` validates and caches generated assets, but no repository image/video generation provider is authorized. The previous `render.py` is a specialized battery schematic, not an arbitrary layer compositor. `graphics/render.py` uses a deterministic Playwright/FFmpeg house-template engine; `graphics/templates/` provides authored animations but no generic semantic-layer mapping. `graphics/media.py` provides FFmpeg lookup/probing. Blender was not available on PATH.

This demo uses an isolated direct route: manually authored semantic plan -> existing scheduler logic via a narrowly gated review-only house-voice handoff -> explicit event-to-layer mapping -> Pillow layer compositing -> existing FFmpeg helper for 1080x1920 H.264/AAC. This is not integrated with the provider selection/AssetStore subsystem or publishing, and does not claim an AI provider executed the plan. The semantic plan is authored in `build_battery_demo.py`, not independently produced by an AI model.

## Demo assets

- `demo_assets/smartphone.png`: AI-generated by the interactive image tool, manually supplied to this repository; fictional generic phone. It is a single still, not AI video.
- `demo_assets/battery_layer.png`, `cross_background.png`, `cross_section.png`, `ion.png`, `energy_meter.png`, `energy_fill.png`, `headline.png`: locally generated procedural graphics. The battery overlay separates from the image; the casing in the original still is **not actually opened**. The battery/ion visualization is simplified and not to scale or a scientific simulation.
- `demo_assets/voice.wav`: approved Option-3 Chatterbox house voice from existing `review-voice.yml`, run `45780216520`; script hash and overall intelligibility 1.0 recorded in `timings.json`. The spoken wording uses “does not” rather than “doesn't”.
- `semantic-plan.json`, `scheduled-blueprint.json`, `layer-design.json`, and `render-timeline.json`: editable plan, scheduled events, explicit mappings, and compiled timeline, respectively. `battery-demo.mp4` is the rendered demonstration.

`review_handoff.py` requires one voice chunk and exact word-for-word match between script tokens and the workflow's recognizer transcript; hence the existing `draft_voice.mapped` matching algorithm has no missing words to interpolate in this case. It validates timestamp monotonicity, measured WAV duration, script fingerprint, and Chatterbox profile. The workflow does not supply per-word confidence or an authenticated hash tying its timing JSON to its WAV. Whisper word boundaries can be inaccurate. This is a **review-only** path and does not produce the trusted `alignment.py` receipt. The original strict `schedule()` remains unchanged.

## Render and reproduction

From the `reels-studio` root, with existing Pillow and system FFmpeg or imageio-ffmpeg:

```
python3 -m graphics.production.build_battery_demo
python3 -m pytest -q graphics/production/test_layer_renderer.py tests/test_visual_execution.py tests/test_production_alignment_semantic.py tests/test_beat_production.py graphics/tests tests/test_voice_handoff.py
```

The first command uses the already-saved `smartphone.png`, `voice.wav`, and `timings.json` and regenerates the procedural PNGs, plans and video. Re-running `python3 -m graphics.production.house_voice_demo` accesses the existing review-only Actions workflow and requires credentials/authorization. It reuses the run recorded in `voice-request.json`; Actions artifacts expire, so preserve the saved voice files. Never put credentials in plans or logs.

`layer_renderer.compile_timeline` checks audio and asset digests, event IDs, timing, target, value types, easing, contiguous beats and transitions. Position, scale, rotation, opacity and camera push/pull are applied to real layers; PNG alpha is supported; JPEG and MP4 inputs are accepted. Fade/cut are explicit. Frames are composed at 540x960 then upscaled by FFmpeg to 1080x1920; FPS is configurable, demo is 24 fps. Audio is AAC encoded once from the house WAV. Frames are quantized to the output frame rate, so durations may differ by up to a frame. Per-beat output is cached, checked for decode and can be regenerated with `force=True`.

## Verified and limitations

Video streams were fully decoded using FFmpeg; output is 1080x1920, 24 fps, 6.21 seconds versus 6.20-second audio, and has an AAC audio stream. Eight frames spanning the rendered video were visually inspected in `review-contact.jpg`. The video was not independently listened to in full in this environment; user audiovisual review is still required. The test suite uses synthetic audio and image/video fixtures for the integration test. It verifies layering/transparency, event boundaries, unsupported effects, invalid assets, MP4 decoding, durations, cache and force behavior.

This remains a proof of concept: no dedicated production cover or voiced house outro, and no scheduling/publishing. The demo is not a polished complete social Short. There is no multi-track sound/music, physically correct 3D, semantic AI planning, scientifically validated depiction, object segmentation, interactive editor, frame-zero cover generation, secured remote receipts, final production QA or user approval. Video layers are decoded into temporary PNGs per beat and may be expensive; synchronous generation and limited safety bounds mean this is not production-grade. The energy indicator is an illustrative graphic, not measured battery telemetry. The still image and procedural layer are separated, not a physical case disassembly. Camera pan is limited to vertical movement plus scaling. Cache storage needs an explicit retention policy. Failures are fail-closed rather than silently substituting stills.
